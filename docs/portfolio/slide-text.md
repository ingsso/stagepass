## ② 문제 — 이전, EC2 수동 배포

```
· 배포할 때마다 프로세스를 내렸다 올려 다운타임이 생김
· 롤백하려면 이전 jar를 찾아 다시 올려야 해 복구가 느림
· 지금 떠 있는 게 어느 커밋인지 서버에 들어가야 알 수 있음
· 배포 절차가 사람의 손과 기억에 의존
```

## ③ 개선 — 이후, 선언형 배포

3단 구성. 소제목 + 한 문장씩.

```
패키징
앱과 의존 서비스를 Helm 차트 하나로 묶고 dev/prod를 values로 분리했습니다.
배포 단위가 릴리스로 추적돼 helm rollback 한 줄로 되돌아갑니다.

동기화
ArgoCD automated sync에 prune·selfHeal을 켜 Git을 단일 진실 공급원으로 만들었습니다.
클러스터를 직접 손대도 Git 상태로 되돌아옵니다.

연결
Actions가 이미지를 GHCR에 올린 뒤 차트의 이미지 태그를 되커밋합니다.
이 커밋 하나가 CI와 CD를 잇는 고리이자 배포 이력 그 자체입니다.
```

**강조 박스 문장** — 다이어그램 아래 또는 개선 블록 끝에

```
배포를 지시하는 주체는 CI가 아니라 Git 저장소의 상태입니다.
Actions는 클러스터에 접근할 자격증명을 갖지 않습니다.
```

> 면접에서 되물어보기 좋은 문장이라 가능하면 살리세요. GitOps를 "왜" 썼는지가 여기 한 줄에 들어 있습니다.

## ⑤ 배운 점

### 01 "에러가 없다"는 "동작한다"가 아니었습니다

```
[슬라이드 압축본]
Prometheus 대시보드가 비어 있는데 에러는 어디에도 없었습니다.
ServiceMonitor의 selector는 Pod이 아니라 Service를 고르는데,
component 라벨을 Pod에만 넣어 매칭되는 Service가 없었습니다.
수집 0건은 실패가 아니라 정상적인 빈 결과로 조용히 통과합니다.
이후 up{job="stagepass"}로 타깃이 실제로 잡혔는지 확인하는 절차를 검증 단계에 넣었습니다.
```

```
[한 줄 컷]
설정을 넣은 것과 동작하는 것은 다릅니다 — 수집 0건이 에러 없이 통과하는 것을 겪고,
지표로 확인하는 절차를 검증 단계에 넣었습니다.
```

### 02 자동화가 자기 자신을 부르는 구조는 설계 시점에 끊어야 합니다

```
[슬라이드 압축본]
CD는 마지막에 values.yaml을 고쳐 되커밋하는데, 그 커밋도 같은 브랜치 push이므로
아무 조치가 없으면 워크플로우가 자기 자신을 무한히 트리거합니다.
paths-ignore 제외 · 커밋 메시지 [skip ci] · GITHUB_TOKEN push는 워크플로우를 트리거하지 않는 정책 —
서로 독립적인 3중 안전장치를 뒀습니다. 하나가 뚫려도 나머지가 막습니다.
```

```
[한 줄 컷]
CD가 되커밋한 태그 범프가 자기 자신을 다시 트리거하는 구조를 만나,
독립적인 3중 안전장치로 끊었습니다.
```

### 03 검증 환경을 만들어 둔 것과 돌려본 것은 다릅니다

```
[슬라이드 압축본]
SSE 알림을 다중 인스턴스로 확장한 뒤, 인스턴스 2개를 띄우는 compose 파일과
검증 스크립트를 저장소에 커밋해 뒀는데 실행 결과 기록이 없었습니다.
실제로 돌려보니 스크립트는 파싱조차 되지 않았고, 페이로드가 깨져
Kafka 메시지가 전부 포이즌 필로 버려지고 있었습니다.
고쳐서 통과시킨 뒤 한 번 더 돌리자 이번엔 애플리케이션 버그가 나왔습니다 —
끊긴 SSE 연결이 던지는 IllegalStateException 이 IOException 만 잡는 catch 를 빠져나가면서
같은 유저의 살아있는 연결까지 알림을 받지 못했습니다.
증거의 기준을 "스크립트가 있다"에서 "통과한 출력이 저장소에 남아 있다"로 바꾸고
실행 로그를 docs/verification 에 커밋했습니다. 12/12 통과, 연속 2회.
```

```
[한 줄 컷]
검증 스크립트를 만들어 둔 것과 돌려본 것은 다릅니다 — 실제로 돌려보니 스크립트도,
애플리케이션도 고장나 있었고, 이후 통과한 실행 로그를 저장소에 남기기로 했습니다.
```

> 이 항목은 GitOps 페이지와 백엔드 페이지 어느 쪽에 붙여도 됩니다.
> GitOps 1장에 넣을 때는 "한 줄 컷"만 쓰고, 수치·아키텍처 설명은 아래 ⑦ 블록으로 빼세요.

## ⑦ (백엔드 아키텍처 페이지용) SSE 수평 확장 검증

> GitOps 1장이 아니라 **백엔드/아키텍처 페이지**에 붙이는 블록입니다.
> 원본 PPT에 실시간 알림 구조를 설명하는 장이 있다면 그 아래에 넣으세요.

**소제목**

```
SSE 수평 확장 — 서버를 늘려도 알림이 도착하는가
```

**문제 → 구조** (2줄)

```
인메모리로 SseEmitter 를 들고 있으면 서버가 2대가 되는 순간 깨집니다.
클라이언트는 서버 A에 붙어 있는데 그 이벤트를 처리한 Kafka 컨슈머는 서버 B일 수 있습니다.
```

```
Kafka Consumer(서버 B) → Redis Publish(notification:{userId})
→ 모든 인스턴스가 PatternTopic("notification:*") 구독 → emitter 를 가진 서버 A만 SSE push
```

**검증 — 숫자 타일 2개 또는 한 줄**

| 수치 | 항목 | 부연 |
|---|---|---|
| **12 / 12** | 검증 항목 통과 | 연결·브로드캐스트·격리·Kafka E2E·LB 경유 |
| **2 회** | 연속 실행 동일 결과 | 컨테이너 재생성 없이 반복 실행 |

```
[한 줄]
인스턴스 2개 + nginx 로드밸런서 환경에서, SSE 연결은 notification-1 / Kafka 컨슈머는
notification-2 인 상태로 알림이 전달되는 것을 확인했습니다 — 검증 항목 12건 전부 통과, 연속 2회.
```

**증거 캡션** (실행 로그 캡처를 넣을 경우)

```
컨슈머는 notification-2 가 잡았고(userId=7 수신 로그), SSE 는 notification-1 에 연결돼 있습니다
— 다른 인스턴스가 처리한 이벤트가 연결된 인스턴스로 도착한다는 뜻입니다.
```

> 파티션 배정은 실행마다 달라지므로, 스크립트는 프로브 메시지로 컨슈머 인스턴스를 먼저 특정한 뒤
> **반대쪽** 인스턴스에 SSE 를 연결해서 검증합니다. 면접에서 "우연히 같은 서버 아니냐"는 반문을
> 받을 수 있는 지점이라, 이 문장은 살려두는 편이 좋습니다.

**기록 위치**

```
docs/verification/sse-scale-verification.md — 실행 출력 전문 · 로그 발췌 · 재현 방법
```
