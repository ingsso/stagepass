StagePass on Kubernetes

EC2에 수동으로 올리던 공연 티켓 예매 서비스를 Helm 차트로 패키징하고, ArgoCD가 Git을 단일 진실 공급원으로 삼아 배포하도록 재구성했습니다. 커밋 한 번이면 이미지 빌드부터 클러스터 반영까지 사람 손이 닿지 않습니다.

2026.08 k3d Helm ArgoCD GitHub Actions GHCR Prometheus

무엇이 문제였고, 무엇을 바꿨는가

문제 → 개선

이전 — EC2 수동 배포

  • 배포할 때마다 프로세스를 내렸다 올려 다운타임이 생김
  • 롤백하려면 이전 jar를 찾아 다시 올려야 해 복구가 느림
  • 지금 떠 있는 게 어느 커밋인지 서버에 들어가야 알 수 있음
  • 배포 절차가 사람의 손과 기억에 의존

이후 — 선언형 배포

패키징

앱과 의존 서비스를 Helm 차트 하나로 묶고, dev/prod를 values.yaml·values-prod.yaml로 분리했습니다. 배포 단위가 릴리스로 추적돼 helm rollback 한 줄로 되돌아갑니다.

동기화

ArgoCD automated sync에 prune·selfHeal을 켜 Git을 단일 진실 공급원으로 만들었습니다. 클러스터를 직접 손대도 Git 상태로 되돌아옵니다.

연결

Actions가 이미지를 GHCR에 올린 뒤 차트의 이미지 태그를 되커밋합니다. 이 커밋 하나가 CI와 CD를 잇는 고리이자, 배포 이력 그 자체입니다.

동기화를 유발한 커밋의 작성자가 github-actions[bot]입니다 — 사람이 아니라 파이프라인이 배포를 일으켰다는 증거입니다. helm rollback으로 이전 리비전 복원도 함께 확인했습니다.

부딪히고 나서야 알게 된 것

배운 점

01

“에러가 없다”는 “동작한다”가 아니었습니다

Prometheus 연동 후 대시보드가 비어 있었는데, 어디에서도 에러가 나지 않았습니다. 원인은 ServiceMonitor의 selector가 Pod이 아니라 Service를 고른다는 것이었습니다. component 라벨을 Pod에만 넣어 두어 매칭되는 Service가 없었고, 수집 대상 0건은 실패가 아니라 정상적인 빈 결과로 조용히 통과했습니다.

그래서 “설정을 넣었다”에서 멈추지 않고 up{job="stagepass"}로 타깃이 실제로 잡혔는지 확인하는 절차를 검증 단계에 넣었습니다. 같은 이유로 Service 셀렉터가 너무 넓어 port-forward가 Redis에 붙던 문제도 이때 함께 드러났습니다.

02

자동화가 자기 자신을 부르는 구조는 설계 시점에 끊어야 합니다

CD는 마지막에 values.yaml을 고쳐 되커밋합니다. 그런데 그 커밋도 같은 브랜치로의 push이므로, 아무 조치가 없으면 워크플로우가 자기 자신을 무한히 트리거합니다.

배포 산출물 경로를 paths-ignore로 제외하고, 커밋 메시지에 [skip ci]를 넣고, GITHUB_TOKEN으로 만든 push는 워크플로우를 트리거하지 않는 정책까지 — 서로 독립적인 3중 안전장치를 뒀습니다. 하나가 뚫려도 나머지가 막습니다.

데모 스코프 — 클러스터는 로컬 k3d이고 PostgreSQL·Redis·Kafka는 인클러스터로 띄웠습니다. 실무라면 EKS 위에서 RDS·ElastiCache·MSK를 바라보게 하고, Secret은 Sealed Secrets 또는 External Secrets로 관리해야 합니다. 차트에는 그 전환 지점을 값(dependencies.*.enabled, secrets.create)으로 남겨 두었습니다.
